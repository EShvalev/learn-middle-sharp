# learn-middle-sharp
Для проектов курса Яндекс Практикум "Продвинутая разработка на C# и .NET"

## Спринт 1, проект "Базовый REST API"
Реализовать базовый REST API с CRUD операциями на основе шаблона webapi (ASP.NET Core Web API)

## Спринт 2, проект "Обработка ошибок, LINQ и тестирование"
Доработать сервис управления событиями:
- добавить глобальный обработчик ошибок
- в метод запроса сообщений добавить фильтрацию + пагинацию
- добавить юнит тесты (связанный проект)

## Спринт 3, проект "Асинхронная обработка и отложенное выполнение"
Доработать сервис управления событиями (мероприятиями):
- добавить новую сущность Booking (бронирование)
- реализовать паттерн "быстрый ответ + отложенная обработка"
- настроить фоновую обработку бронирований
- добавить юнит тесты для новой сущности Booking

## Спринт 4, проект "Параллельная обработка и синхронизация"
Доработать сервис управления событиями (мероприятиями):
- добавить в структуру события Event поля для резервирования мест + методы для резервирования/освобождения мест
- реализовать в BookingService при создании брони защиту критической секции для безопасного конкурентного бронирования
- реализовать в фоновом BookingProcessingService защиту критической секции при обработке брони + логику подтверждения/отмены/обработку ошибок

## Спринт 5, проект "Основы EF Core и работа с данными"
Доработать сервис управления событиями (мероприятиями):
- подключить к проекту PostgreSQL через Entity Framework (EF)
- настроить маппинг сущностей Event и Booking с помощью Fluent API
- реализовать DBContext с DbSet для сущностей Event и Booking
- интегрировать DBContext в EventService и BookingService, заменив in-memery коллекции на аналоги из EF
- доработать фоновый BookingProcessingService для коректной работы с scoped-зависимостями
- адаптировать юнит тесты под использование EF

## Подключение БД

В данном проекте используется БД PostgreSQL через Docker контейнер.

### Запуск Docker контейнера БД на Windows
1. Поднять на локальном компьютере Docker:
	- включить в BIOS использование WSL 2
	- установить приложение Docker Desktop (скачать отсюда https://www.docker.com/products/docker-desktop/)
	- открыть Docker Desktop 
2. Конфигурация контейнера для PostgreSQL, БД eventapi и строки подключения находится в файле [docker-compose.yml](./docker-compose.yml) в корневой папке решения.
3. Cтрока подключения к БД настраивается в файле [appsettings.json](./EventApi/appsettings.json) путем добавления секции ConnectionStrings:
   ```
   {
	  "ConnectionStrings": {
		"DefaultConnection": "Host=localhost;Port=5432;Database=eventapi;Username=postgres;Password=postgres"
	  },
   ...
   }
   ```
   **Замечание**: Параметры строки подключения в appsettings.json и в docker-compose.yml должны быть согласованы.
3. Запустить из корневой папки решения команду

	`docker compose up -d`

	Данная команда создает контейнер eventapi-postgres с СУБД PostrgeSQL, в нем БД eventapi. 
4. При первом запуске приложения EventApi указанный ниже код проверяет, не создана ли еще схема БД (схема core, в ней таблицы, связи, ограничения и т.д.) и если нет, 
	создает их (только 1 раз при первом запуске).

	```
	using (var scope = app.Services.CreateScope())
    {
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        db.Database.EnsureCreated();
    }
	```
	После этого возможна работа с БД средствами EF.
5.  Для остановки контейнера запустить из корневой папки решения команду

	`docker compose down`

	После этого доступ к БД невозможен.
6.  Иногда нужно остановить контейнер с полным удалением данных. Для этого используется команда

	`docker compose down -v`

	После этого том БД eventapi_pgdata удаляется вместе со всеми таблицами и т.д. При последующем поднятии контейнера eventapi-postgres БД будет пуста, 
	и при первом запуске приложения EventApi все объекты БД eventapi будут созданы заново.

## Краткое описание API
Все методы относительно корневого пути [protocol]//[host]:[port]

| HTTP метод | Путь | Параметры | HTTP Код: Назначение |
| --- | :--- | :--- | :--- |
| GET | /api/events?title=str&from=dat&to=dat | Фильтрация: [FromQuery] title: по названию, [FromQuery] from: по дате StartAt, начало интервала (>=), [FromQuery] to: по дате StartAt, окончание интервала (<=) | 200: Возвращает список событий с фильтрацией (все параметры опциональные)<br/> 500: Внутренняя ошибка сервера |
| | ...&page=int&pageSize=int | Пагинация: [FromQuery] page: номер страницы (по умолчанию 1), [FromQuery] pageSize: размер страницы (по умолчанию 10) | и пагинацией (параметры также опциональные) |
| GET | /api/events/\{id\} | [FromRoute] id: Id события | 200: Возвращает событие по Id<br/> 404: Событие не найдено<br/> 500: Внутренняя ошибка сервера |
| POST | /api/events |  [FromBody] eventReq: структура события | 201: Добавляет новое событие<br/> 400: Ошибка валидации<br/> 500: Внутренняя ошибка сервера |
| PUT | /api/events/\{id\} |  [FromRoute] id: Id события, [FromBody] eventReq: структура события | 204: Обновляет событие данными из eventReq<br/> 404: Событие не найдено<br/> 400: Ошибка валидации<br/> 500: Внутренняя ошибка сервера |
| DELETE | /api/events/\{id\} | [FromRoute] id: Id события | 204: Удаляет событие по Id<br/> 404: Событие не найдено<br/> 500: Внутренняя ошибка сервера |
| POST | /api/events/\{id\}/book | [FromRoute] id: Id события | 202: Добавляет новое бронирование для события (отложенное создание, обрабатывается в фоновом сервисе)<br/> 404: Событие Id не найдено<br/> 409: Недостаточно мест<br/> 500: Внутренняя ошибка сервера |
| GET | /api/bookings |  | 200: Возвращает список всех бронирований по всем событиям<br/> 500: Внутренняя ошибка сервера |
| GET | /api/bookings/\{id\} | [FromRoute] id: Id бронирования | 200: Возвращает бронирование по Id<br/> 404: Бронирование не найдено<br/> 500: Внутренняя ошибка сервера |

## Модели данных

### Событие (Event)

Структура события eventReq (передается в теле запросов POST, PUT):

	{
		"title": "string" [required],
		"description": "string",
		"startAt": "2026-09-28T16:42:50.411Z" [required],
		"endAt": "2026-09-28T18:42:50.412Z" [required][must be: endAt > startAt],
		"totalSeats": "int" [required][must be > 0]
	}

Структура события eventDto (возвращаемая GET запросами):

	{
		"id": "guid" [id события],
		"title": "string" [заголовок],
		"description": "string" [описание],
		"startAt": "2026-09-28T16:42:50.411Z" [дата/время начала],
		"endAt": "2026-09-28T18:42:50.412Z" [дата/время начала],
		"totalSeats": "int" [общее количество мест],
		"availableSeats": "int" [количество свободных мест]
	}

Структура ответа при запросе списка событий:

	{
		"items": [
			{
				"id": "guid",
				"title": "string",
				"description": "string",
				"startAt": "2026-09-28T16:42:50.411Z",
				"endAt": "2026-09-28T18:42:50.412Z",
				"totalSeats": "int",
				"availableSeats": "int"
			},
			... [список событий]
		],	
		"page": int [номер текущей страницы],
		"pageSize": int [размер страницы],
		"totalCount": int [общее количество событий],
		"totalPages": int [общее количество страниц],
	}

### Бронирование (Booking)

Структура бронирования (возвращаемая GET запросами):

	{
		"id": "guid" [auto],
		"eventId": "guid" [required],
		"status": "int" [required, auto],
		"createdAt": "2026-10-28T16:42:50.411Z" [required],
		"processedAt": "2026-10-28T18:42:50.412Z" [автозаполняется при Confirm/Reject]
	}

Статусы бронирования (перечисление):

	enum BookingStatus
    {
        Pending = 1,
        Confirmed = 2,
        Rejected = 3
    }

Для обеспечения целостности изменений количества свободных мест при бронировании в связанном событии реализован класс KeyedLockManager (менеджер гранулярных блокировок по Id объекта)
с автоматической очисткой после выхода из блока using. Он создает асинхронную блокировку (внутри вызывается SemaphoreSlim) при вызове метода AcquireLockAsync. Для объектов типа Event
добавлен метод расширения AcquireEventLockAsync. 

**Замечание**: Ранее в разных сервисах использовались разные примитивы синхронизации (синхронный lock в BookingService, асинхронный SemaphoreSlim в фоновом сервисе).<br />
**Замечание**: После добавления KeyedLockManager CAS вызовы в методах TryReserveSeats и ReleaseSeats заменены на обычный декремент/инкремент, чтобы не смешивать разные типы блокировки.

Сервис бронирования BookingService использует блокировку в следующих операциях:
- при создании брони Create (счетчик event.AvailableSeats уменьшается)
- при отказе от брони Reject (счетчик event.AvailableSeats увеличивается) 

**Замечание**: При подтверждении брони Confirm счетчик не меняется, критическая секция не нужна.

Для обработки бронирований запущен фоновый процесс, в нем бесконечный цикл обработки по таймеру (PeriodicTimer) с интервалом 5 сек. 
При каждом проходе: 
1. Запрашивается список бронирований в начальном статусе Pending. 
2. Для каждого бронирования запускается своя задача, в которой выполняется имитирующая удаленный вызов задержка в 2 сек, затем следующая логика, обернутая в критическую секцию с помощью KeyedLockManager:<br/>
   2.1. Проверяется, что событие бронирования существует:
    - Если да, бронирование переводится в статус Confirmed, бронь сохраняется (имитация).
    - Если нет, бронирование переводится в статус Rejected, бронь сохраняется (имитация).
   2.2. Если в процессе обработки возникло исключение OperationCanceledException с условием IsCancellationRequested=true, выполнение прерывается, исключение пробрасывается наверх для остановки цикла обработки.<br/>
   2.3. Если в процессе обработки возникло непредвиденное исключение, бронь отменяется и сохраняется (имитация) + если связанное событие еще существует, в нем возвращается ранее зарезервированное место в AvailableSeats.<br/>
3. Все задачи выполняются одновременно через единый вызов ожидания Task.WhenAll.

Допустимые переходы между статусами бронирования:

	Pending -> Confirmed
	Pending -> Rejected
	Confirmed -> Rejected

При выполнении допустимого перехода поле processedAt автоматически заполняется текущей датой/временем.
При попытке недопустимого перехода выбрасывается исключение BookingStatusException.

Пример сценария использования:
1. POST /api/events - создать новое событие с TotalSeats = 5. Запомнить из ответа Id события (eventId).
2. POST /api/events/{eventId}/book - быстро вызвать 5 раз подряд, создать несколько бронирований для события.
3. GET /api/bookings - сразу же проверить, что бронирования созданы в статусе Pending, поле processedAt не заполнено.
4. GET /api/bookings - спустя время проверить, что статус бронирований изменился на Confirmed, поле processedAt заполнено.
5. POST /api/events/{eventId}/book - вызвать еще раз, чтобы сработал сценарий overbooking, сервис должен вернуть HTTP 409 (conflict).

## Обработка ошибок
Ошибки перехватываются централизованно с помощью обработчика GlobalExceptionHandlingMiddleware. В нем они логируются и приводятся к единому формату ProblemDetails.

При ошибках возвращается структура ProblemDetails:

	{
	  "type": "string",   // Ссылка на документ с описанием типа ошибки (URI параграфа в RFC 9110)
      "title": "string",  // Краткое описание типа ошибки
	  "status": int,      // HTTP код ошибки
	  "detail": "string"  // Текстовое описание ошибки
	}

**Замечание**: Ниже приведена таблица маппинга исключений в HTTP ошибки.

| Исключения | HTTP ошибки |
| --- | :--- |
| BookingStatusException | 400 (bad request) |
| VaildationException | 400 (bad request) |
| NotFoundException | 404 (not found) |
| NoAvailableSeatsException | 409 (conflict) |
| все прочие Exception | 500 (internal server error) |
